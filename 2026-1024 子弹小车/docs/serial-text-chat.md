# 电脑串口文字测试

## 当前模式

当前 PlatformIO 配置启用 `CONFIG_SERIAL_TEXT_CHAT=y`。电脑发送一行文字，设备通过原平台连接上传，服务端返回的 `tts.sentence_start.text` 打印到串口。

测试模式关闭麦克风上传、唤醒检测、自动监听和小车动作输出；不会初始化小车业务 UART/LED。收到 `tts.start` 后汇总各段文字，等待明确 `is_aborted=false` 的 `tts.stop` 后校验格式。校验通过输出“格式正确”，再转换并显示状态字节及 `AA 55 STATE CRC8` 帧；校验未通过只输出“格式错误”，不转换、不输出零状态帧、不更新动作状态。测试阶段始终不执行动作或发送业务 UART 指令。联网、激活、WSS、令牌与平台原有恢复方式继续使用原实现，系统提示音保留。

平台角色提示词不由固件修改。如果平台仍配置为只返回五字段动作 JSON，串口也会显示该 JSON；测试模式不会执行这些动作。

左右转字段分别兼容 `turn_left`/`turnleft`、`turn_right`/`turnright`，可混用，但同一个动作字段不能出现两次。其余字段仍为 `forward`、`backward`、`fire`，五个字段必须齐全，值必须为字符串 `on` 或 `off`。

例如下面两段会先拼接，再作为一个完整对象校验：

```text
[AI] {"forward":"off",
[AI] "backward":"on","turnleft":"off","turnright":"off","fire":"off"}
格式正确
[状态字节] 00000010 (0x02)
[二进制数据] 10101010 01010101 00000010 10001100
[十六进制帧] AA 55 02 8C
[串口测试] 回复结束
```

`Display: Role:assistant` 等是界面模块重复记录同一片段，不参与缓冲拼接。重复 start 不会清空已收集文字，重复 stop 不会再次解析。JSON 格式错误、未完整开始、被中断、缺少明确结束标记或超过 8192 字节的回复，均只报告“格式错误”，不生成动作帧；断线/错误会清理当前缓冲。合法的五字段全 `off` 仍是“格式正确”，会显示全零状态对应的测试帧。

二进制数据为每字节 8 位、从高位到低位的可读表示，只打印到电脑控制台；十六进制帧是同一数据的另一种显示方式，不代表已经向 STM32 发送。

## 操作

1. 使用本工程已经核对过硬件配置的固件，按原方式完成 Wi-Fi 配网与平台绑定。
2. 串口助手打开能看到启动日志的 COM 口，设置 **115200、8N1、无流控、UTF-8、文本发送**，关闭十六进制发送。
3. 等待 `[串口测试] 平台配置就绪，请发送一行文字`。
4. 发送 `你好，请介绍一下你自己`，发送末尾添加 LF、CR 或 CRLF 任意一种换行。仅点击发送但没有换行时，设备会继续等待完整一行。
5. 观察 `[已发送]`、`[AI]` 和 `[串口测试] 回复结束`。上一轮结束后再发送下一句。

当前配置同时支持 UART0 控制台（通常经 USB 转串口芯片）和 ESP32-S3 原生 USB Serial/JTAG 控制台，两者的输入各自组帧，输出沿用已有日志控制台。不新增接线或指定 GPIO；不要连接小车与 STM32 通信的业务串口来做此测试。若只连接其中一个端口，使用该端口即可。

不要同时让串口监视器和串口助手占用同一个 COM 口。中文乱码时核对接收与发送编码都是 UTF-8。板级麦克风、屏幕、PSRAM 等配置仍需与实际硬件一致，文字模式不能替代硬件适配。

## 输入与提示

- 每行最多 1024 **字节**，中文通常占 3 字节；超长整行丢弃，不发送截断内容。
- 空行或仅空格、制表符的行会提示并忽略。
- 非法 UTF-8、NUL、终端控制字符会整行拒绝；输入按普通文本处理，不提供退格编辑或终端命令。
- 每次只处理一条请求。处理期间收到的其他完整行会提示忙，不排队、不自动补发。
- 未联网、未激活或设备正在进行其他操作时提示尚未就绪，请在条件恢复后重新发送。
- 连接/发送失败、会话关闭、平台错误或网络断开会显示提示，结束当前请求；不增加自动重传。
- 服务端 `tts.stop` 标记本轮结束；中断或缺少明确完成标记会注明。没有收到结束事件时，不会假装完成；本轮未新增无响应超时，必要时重启设备后重新测试。

## 协议与验证边界

文字复用现有 `listen/detect` 入口，消息为：

```json
{"session_id":"当前会话","type":"listen","state":"detect","text":"电脑输入的文字"}
```

会话未打开时先走原有 hello/认证流程；使用 cJSON 序列化文字，正确转义引号与反斜杠。网络回调复制文字后交由应用主任务处理；设备只展示服务端回复，不本地生成回答。

项目原说明将 `detect` 定义为唤醒文字入口，平台是否把任意文字交给 AI、是否返回完整 TTS 事件，仍需真实账号和设备联调。`[已发送]` 只表示本地传输接口发送成功，不能证明 AI 已接受或已回复。

电脑端测试：

```powershell
pio test -d test-native -e serial_tests -e car_tests
```

固件编译：

```powershell
pio run -e esp32s3
```

关闭测试模式可通过 menuconfig 将 `SERIAL_TEXT_CHAT` 设为 n，同时将 `sdkconfig.defaults.platformio` 中的对应项改为 n，再重新编译。已有 `sdkconfig.esp32s3` 时仅修改 defaults 不会覆盖已保存配置。关闭后恢复原有语音与小车配置。

## 软件验证记录（2026-10-24）

- 串口输入 5 组测试通过：逐字节中文/特殊字符、CR/LF/CRLF 与多行、空白与未结束输入、1024 字节边界与超长后的恢复、非法 UTF-8/控制字符、两个端口独立组帧。
- 小车解析、回复汇总与帧转换 12 组、串口输入 5 组测试通过，共计 17 组；包含左右字段 4 种写法组合与全部 32 种动作状态、别名重复拒绝、上述后退回复在每个字节边界分段后均得到 `0x02`，以及全零/后退/组合动作帧的固定二进制向量。
- 直接调用实际 `Protocol::SendUserText` 进行电脑端检查，确认四个 JSON 字段、会话与输入文字完整往返、引号/反斜杠转义、输入不能注入其他协议字段、发送失败返回 false。
- 使用单独的关闭模式配置副本，检查 `application.cc` 在关闭 `SERIAL_TEXT_CHAT` 后仍可编译；没有改动用于最终固件的开启模式配置。
- 当前测试阶段“校验后转换”的固件构建成功，实际启用 `CONFIG_SERIAL_TEXT_CHAT`；静态 RAM 77,308 / 327,680 字节（23.6%），应用 2,638,227 / 4,128,768 字节（63.9%），固件为 `.pio/build/esp32s3/firmware.bin`。整轮校验缓冲占用约 8 KiB 静态 RAM。
- 尚未烧录或验证真实串口收发、平台任意文字入口、AI 回复以及断线后的实机行为。
